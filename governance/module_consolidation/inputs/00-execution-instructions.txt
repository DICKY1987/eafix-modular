3. Authority architecture that must exist after cutover

Use this exact logical model:

EAFIX AUTHORITIES

|

+-- 34 module-root manifest.json files

|   +-- authoritative for module-specific purpose

|   +-- boundaries and responsibilities

|   +-- module-local behavior

|   +-- module process-step participation

|   +-- module-owned file definitions

|   +-- module-local use of shared files

|   +-- module contract obligations

|   +-- module runtime/operations/safety details

|   +-- field-level provenance and reconciliation status

|

+-- EAFIX_auth_docs/01_canonical_registries/process_registry.jsonl

|   +-- authoritative for global process step identity, order, global process behavior,

|       and cross-module process topology

|

+-- global contracts/identifier/schema authorities

|   +-- authoritative for shared payload structure and compatibility

|

+-- EAFIX_auth_docs/01_canonical_registries/shared_file_registry.json

|   +-- authoritative for global shared-file consumer topology

|

+-- repository-wide governance authorities

    +-- naming, lifecycle, safety, document authority, etc.

Derived outputs may exist, but they are one-way projections:

34 module manifests + global authorities

        |

        +--> generated 34-manifest bundle

        +--> generated context packets

        +--> generated module catalog/index

        +--> generated diagrams

        +--> generated AI references

        +--> generated reports

        +--> GitHub Project tracking views

Never create a bidirectional authority loop.

Wrong:

root manifest <--> bundle <--> old catalog <--> context packet

Correct:

reviewed evidence -> reconciliation -> approved module manifest -> projections

8. Required v2 manifest information model

The v2 schema must be expressive enough that one module manifest can serve as a complete AI context package for that module without reproducing system-wide facts unnecessarily.

At minimum provide structured sections for:

8.1 Identity and lifecycle

	●	permanent 20-digit module ID;
	●	short ID m####;
	●	canonical symbol;
	●	canonical root;
	●	canonical human-readable name;
	●	aliases and legacy names;
	●	identity status;
	●	lifecycle status;
	●	manifest/specification version;
	●	schema version;
	●	effective baseline commit;
	●	accountable owner or approval authority.

8.2 Purpose and boundaries

	●	purpose;
	●	responsibilities;
	●	explicit exclusions;
	●	owned capabilities;
	●	side effects;
	●	trust boundary;
	●	externally visible behavior where applicable.

8.3 Process participation

Change the v1 compulsory single binding into zero-to-many process-step references.

A reusable/shared module such as SK1 or SK2 must not be forced to invent a fake step.

Each process-step entry must reference a real process record when one exists and contain only the module-local context needed to execute or understand that step:

	●	step_id
	●	step_code
	●	process_registry_ref
	●	trigger
	●	preconditions
	●	inputs
	●	processing
	●	decisions
	●	primary_output
	●	secondary_outputs
	●	validation
	●	failure_output
	●	retry_timeout_recovery
	●	observability
	●	exclusive_files
	●	shared_files
	●	contract_refs
	●	state_transition_refs
	●	completion_criteria
	●	next_handoff_refs

Do not independently redefine the global process order inside every module manifest.

8.4 Module-owned file definitions

Define each module-owned file once at module level.

Recommended fields:

	●	file_id
	●	path
	●	role
	●	required
	●	ownership_status
	●	current_or_proposed_location
	●	content_sha256 where practical
	●	entrypoint
	●	runtime_relevance
	●	contracts_produced
	●	contracts_consumed
	●	evidence_refs

Roles should be controlled values such as:

	●	entrypoint
	●	library
	●	schema
	●	config
	●	fixture
	●	test
	●	doc
	●	data
	●	tooling
	●	runtime_asset
	●	other:<controlled-token>

Do not claim a proposed physical path is current.

8.5 Step-specific file usage

For every process step, list all files required by that step in exactly two logical groups:

exclusive_files

Files used only by that step within the module.

shared_files

Files also used by another step or module.

A local shared-file reference contains only what the current step needs:

{

  "file_id": "FILE-X",

  "path": "relative/path/to/file.ext",

  "role_in_this_step": "validation_helper",

  "required": true

}

Do not put the complete consumer genealogy in the module manifest.

8.6 Shared-file registry

Create global consumer topology in:

EAFIX_auth_docs/01_canonical_registries/shared_file_registry.json

Recommended record shape:

{

  "file_id": "stable-id",

  "path": "repository/relative/path",

  "content_sha256": "sha256-if-applicable",

  "file_role": "library",

  "ownership_class": "global_shared|module_owned_shared_use",

  "steward": "module-or-global-authority",

  "status": "active",

  "consumers": [

    {

      "module_id": "50000000000000000001",

      "module_short_id": "m0001",

      "step_id": "60000000000000000001",

      "usage_role": "configuration_source",

      "required": true

    }

  ],

  "provenance": []

}

This registry is authoritative for the question:
“Who else consumes this shared file?”

Each module manifest remains authoritative for:
“What files does this module/step require?”

11. Blocker-resolution algorithm

Historical work once produced a queue with thousands of open records. Do not trust the historical count as current. Rebuild the queue from the fresh baseline.

For every open record:

	1.	Resolve the target fact class:
	●	module-specific;
	●	process-global;
	●	contract-global;
	●	shared-file-global;
	●	governance-global;
	●	implementation observation;
	●	derived/projection-only.
	2.	Locate the correct active authority for that fact class.
	3.	Compare the candidate claim against the current authority.
	4.	Apply these deterministic rules:

Rule A: already identical

If the candidate claim is semantically identical to the authority:

	●	disposition = ALREADY_COVERED;
	●	record evidence;
	●	no manifest mutation.

Rule B: duplicate historical wording

If multiple sources express the same fact:

	●	designate the stronger/active evidence;
	●	disposition duplicates as MERGE or ALREADY_COVERED;
	●	do not create duplicate fields.

Rule C: old source conflicts with stronger active authority

If an older source conflicts with the canonical process, contract, governance, or approved module decision:

	●	disposition = REJECTED;
	●	cite the active authority and decision;
	●	do not change the authority merely because the source is older or more verbose.

Rule D: fact belongs to external authority

If a module-supporting document contains a global process/contract/governance fact:

	●	disposition = RETAINED_EXTERNAL;
	●	manifest gets a stable reference where needed;
	●	do not copy the global definition into every module.

Rule E: supported module fact is missing

If direct evidence supports a module-specific fact that is missing:

	●	disposition = MIGRATE;
	●	generate a guarded patch;
	●	do not apply before semantic review/approval.

Rule F: current value and candidate both contain useful non-conflicting information

	●	disposition = MERGE;
	●	produce the exact merged result;
	●	preserve provenance from both.

Rule G: genuine ambiguity

If two plausible meanings remain:

	●	mark knowledge = conflicted or deferred;
	●	create conflict record;
	●	keep the blocker visible;
	●	do not guess.

Rule H: apparent N/A

Only use not_applicable after proving the field genuinely does not apply under the module’s profile and recording the governing rule.

27. File and process relationship rules

30. Definition of specification-ready

A module is specification_ready = true only if:

	●	it validates against v2;
	●	its identity is approved;
	●	every applicable mandatory field is confirmed;
	●	unknown mandatory facts are resolved;
	●	conflicts are resolved or an approved policy explicitly allows deferral without claiming readiness;
	●	process refs resolve;
	●	contract refs are exact or tracked as permitted non-blocking external gaps;
	●	required file inventory is reconciled;
	●	module-local behavior and failure semantics are sufficient for its profile;
	●	provenance is complete for accepted changed values;
	●	no shadow module authority contradicts it.

A module can be specification-ready even if implementation work remains. Keep implementation_verified separate.



31. Definition of fully scraped

A source version is fully scraped only when:

	●	every relevant section was reviewed;
	●	every relevant atomic claim was extracted;
	●	every claim has a final disposition;
	●	accepted claims are applied and verified;
	●	rejected claims have reasons;
	●	retained-external claims point to the live authority;
	●	conflicts are resolved or explicitly governed as deferred;
	●	no extraction row remains unprocessed;
	●	affected authorities validate.

Scanning/OCR/indexing is not equivalent to fully scraped.



32. Definition of safe to archive

A fully scraped source is safe to archive only when:

	●	it is not an active authority;
	●	it is not a required live input to tooling;
	●	no unresolved relevant claim depends on it;
	●	all active references are updated or intentionally historical;
	●	the archive destination/receipt is prepared;
	●	restoration is possible;
	●	the approved retention policy permits archival.

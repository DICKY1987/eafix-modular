contracts/ — Full Breakdown
This folder is the shared contract layer for the whole system: schemas, models, and validators that define the wire formats every module must speak. It’s referenced by nearly every one of the 34 module manifests (as "shared", not owned), which is consistent with what you’ve already found about the 19 modules claiming zero unique ownership.

1. Top-level validators (2099900014..., 2099900015... + shims)
	•	CSVArtifactValidator (2099900014260118_validate_csv_artifacts.py): validates CSV artifacts against the 4 schema models (ActiveCalendarSignal, ReentryDecision, TradeResult, HealthMetric), checking headers, file_seq monotonicity, and checksum_sha256 integrity.
	•	JSONSchemaValidator (2099900015260118_validate_json_schemas.py): validates JSON against schema files + Pydantic models using jsonschema.Draft202012Validator.
	•	The clean-named validate_csv_artifacts.py / validate_json_schemas.py are ID-loader shims — they use importlib.util.spec_from_file_location to dynamically load the ID-prefixed implementation file and re-export it under a clean import name, then subclass it to add ID-prefix-aware filename parsing (e.g. detect_csv_type strips a leading \d+_ before matching). This is the exact same shim pattern flagged in your memory as the highest-risk migration dependency (services _id_loader.py pattern) — just implemented inline here rather than via a shared loader module.

Notable findings for your governance work:
	1.	models/2099900019260118___init__.py is a dead duplicate of models/__init__.py — safe removal candidate.
	2.	The contracts/ folder is claimed as shared by essentially every module manifest, confirming it’s infrastructure, not owned by any single module — it probably belongs in your artifact/reuse registry rather than the module registry.
	3.	The ID-loader shim pattern here (inline spec_from_file_location per shim) differs from the services/_id_loader.py centralized pattern noted in your memory — two different implementations of the same idea across the repo, which is itself worth a DEC-REG entry if you want one canonical pattern.
	4.	orders_in.schema.json / orders_out.schema.json are missing $schema declarations that the other two JSON schemas have — small SSOT consistency gap.

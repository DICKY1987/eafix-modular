Technical Execution Processes for Each GitHub
Workspace Solution
This document translates the high‑level mapping from the previous report into concrete technical
processes for implementing each part of a phase‑process template in GitHub Projects. Where possible it
references existing documented workflows (docs or sample repositories) and then extends them with
custom procedures. The goal is to enable an autonomous execution flow: issues and pull requests are
automatically created, triaged, progressed through phases, gated by CI checks and visualised via roadmaps
and charts.

2. Mapping Step Contracts to Issues and Sub‑issues
2.1 Create issues for each step contract
1.
2.
3.
For each step in your process, create an issue using templates that capture metadata: Phase field
(default value: current phase), Step ID, Effort estimate, target date and gate requirements. Use issue
forms or issue fields so values are typed and mandatory.
When a contract is complex, create sub‑issues for sub‑steps. GitHub allows up to 100 sub‑issues per
issue and eight levels of nesting 5
. Sub‑issues display their relationship to the parent issue and
6
their progress contributes to the parent’s Sub‑issue progress field .
Use the Parent issue field in the project to group items by their parent. You can filter by parent issue
6
ID (e.g., parent‑issue:"owner/repo#123" ) .
2.2 Automate creation of issues and sub‑issues
An example from an open‑source repository ( ohmyzsh ) demonstrates how to add issues or pull requests
to a project via the GraphQL API:
# .github/workflows/project.yml (excerpt)
- name: Read project data
run: |
gh api graphql -f query='query($org: String!, $number: Int!)
{ organization(login: $org){ projectV2(number: $number) { id fields(first:20)
{ nodes { ... on ProjectV2Field { id name } } } } } }' -f org=$ORGANIZATION -F
number=$PROJECT_NUMBER > project_data.json
cat >> $GITHUB_ENV <<EOF
PROJECT_ID=$(jq '.data.organization.projectV2.id' project_data.json)
EOF
- name: Add to project
env:
ISSUE_OR_PR_ID: ${{ github.event.issue.node_id ||
github.event.pull_request.node_id }}
run: |
item_id="$(gh api graphql -f query='mutation($project: ID!, $content: ID!)
{ addProjectV2ItemById(input: {projectId: $project, contentId: $content}) { item
{ id } } }' -f project=$PROJECT_ID -f content=$ISSUE_OR_PR_ID --jq
'.data.addProjectV2ItemById.item.id')"
echo "ITEM_ID=$item_id" >> $GITHUB_ENV
This workflow retrieves the project ID, then adds an issue or PR to the project using the
addProjectV2ItemById mutation 7
. You can extend this script to create a new issue via the GitHub
API and immediately add it to the project.

After adding an item, set its fields (Phase, Effort, etc.) using the updateProjectV2ItemFieldValue
mutation. The ohmyzsh workflow shows how to set text fields (e.g., Plugin, Theme ) by specifying the

- name: Fill Pull Request fields in project
run: |
gh api graphql -f query='mutation ( $project: ID!, $item: ID!,
$plugin_field: ID!, $plugin_value: String!, $theme_field: ID!, $theme_value:
String! ) { set_plugin: updateProjectV2ItemFieldValue(input: { projectId:
$project, itemId: $item, fieldId: $plugin_field, value: { text:
$plugin_value } }) { projectV2Item { id } } set_theme:
updateProjectV2ItemFieldValue(input: { projectId: $project, itemId: $item,
fieldId: $theme_field, value: { text: $theme_value } }) { projectV2Item
{ id } } }' -f project=$PROJECT_ID -f item=$ITEM_ID -f
plugin_field=$PLUGIN_FIELD_ID -f plugin_value=$PLUGIN -f
theme_field=$THEME_FIELD_ID -f theme_value=$THEME --silent

3. Mapping Gates to CI Checks and Required Status Checks
3.1 Implement gate checks in GitHub Actions
1.
2.
3.
For each gate (e.g., design review, unit tests, security scan), create a separate job in a GitHub Actions
workflow. Each job runs the relevant validation and should fail if the gate is not satisfied.
Jobs produce status checks. When status checks are required for a branch, the pull request cannot
8
merge until they pass .
Optionally publish gate results to the associated issue via the Checks API or comment. You can also
update a custom field (e.g., Gate status ) in the project via GraphQL.
3.2 Configure branch protection rules
1.
2.
Go to Repository Settings → Branches. Under Branch protection rules, select the base branch
(e.g., main ) and enable Require status checks to pass before merging.
Choose the checks corresponding to your gate workflows. Only commit statuses that have
8
completed successfully in the last week can be selected .
3.3 Update project gate field after checks
Use a post‑CI step to update the gate status in the project. For example, after tests pass, run a command similar to Section 2.3 to set the Gate field to Passed or Failed .

4. Mapping Execution to Pull Requests and Linking Issues
4.1 Link pull requests to issues
1.
2.
In the pull request body, include Closes #<issue_number> or Fixes #<issue_number> to
automatically close the issue upon merge.
Alternatively, use GitHub’s Link PR feature on the issue page. The PR will appear under Linked pull
requests.

4.3 Set issue status when PR is opened/merged
Built‑in workflows automatically set the Status field to Todo when an item is added and Done when its

6.2 Use iteration fields for sprints
1.
Create an Iteration field. When created, it automatically generates three iterations; you can add
13

2.
3.

Roadmaps display iterations as colored blocks; you can drag items between iterations.

7. Metadata and Priority with Issue Fields
7.1 Enable organization‑wide issue fields
Issue fields (in public preview) provide typed metadata like Priority, Effort, Start date and Target date. They
are defined at the organization level and available across all repositories. You can search, filter and report
on these fields and integrate them into project views 15
. Issue field values can be edited directly in the
16 17
project table and are synced back to the underlying issues .
7.2 Using custom number and text fields
Add number fields to track story points, complexity or risk. Text fields can capture references or notes.
18
These fields support filters and range queries .
7.3 Set default values for fields
GitHub’s April 9 2026 update allows default values for text, number and single‑select fields. Define defaults
19
(e.g., Phase defaults to PH‑00 , Priority defaults to Medium ) so new items inherit baseline metadata .

8.1 Configure built‑in workflows
In the project settings → Automations, enable workflows:
•
•

Auto‑add – automatically adds new issues/PRs from specified repositories based on filters such as

9. Putting It All Together
By following these technical processes, you can implement a self‑driving project board aligned with your
phase‑process template:
1.
2.
3.
4.
5.
6.
Create the project with custom fields for Phase, Priority, Effort, Start/Target date and a Gate status.
Define milestones for each phase and set up iterations for sprints.
Standardise issue templates that include fields for phase, step ID and gating requirements. Use
sub‑issues to decompose complex steps.
Automate intake: use built‑in auto‑add rules and actions/add-to-project to capture new
issues and PRs into the project and set default fields.
Drive progression: configure CI workflows as gates; require their status checks to pass before
merging. Use GraphQL actions to update the Phase field and gate status when conditions are met.
Track and visualise: close issues to complete steps; use milestone and sub‑issue progress, burn‑up
charts and roadmaps to monitor progress across phases.
Refine automation: iterate on rules and scripts to improve triage, field updates and gating. Use
19
default field values and issue fields to reduce manual data entry .
These processes enable a GitHub project to mirror your phase‑process template, drive work autonomously
via automations and CI checks, and provide high‑level visibility through roadmaps and insights.
